# ROADMAP

Версія 0.1.0 закриває базові запити: одна або кілька тем чи кошиків × до ~10 мовних розділів, вердикт,
довіра, графік, PDF, перевірка чисел і уточнення без повторного завантаження. Нижче описано, як я б
розвивав скіл для складніших досліджень і більших обсягів даних. Порядок відповідає цінності для
користувача та ризику помилкових висновків.

## v0.2 — тема замість статті

Головне обмеження зараз у тому, що тему представляють 1–5 статей, і їх обирає агент.

- **Автоматичне розширення кошика.** З теми у Wikidata брати пов'язані статті:
  - головну категорію (P910) і її підкатегорії з обмеженням глибини;
  - «див. також» і вихідні посилання головної статті;
  - PetScan для перетину категорій;
  - `articletopic:` у пошуку Вікіпедії (класифікатор тем ORES/Lift Wing).

  Для кожної статті показувати її внесок, щоб користувач бачив, із чого складається тема.
- **Leave-one-out для кошика.** Рахувати, чи тримається вердикт без кожної статті по черзі. Якщо весь
  «ріст» дає одна стаття, це треба сказати.
- **Ідеї тем від скіла.** Для «що ще додати в застосунок?» брати сусідні теми з тих самих категорій,
  ранжувати їх за часткою й динамікою і показувати прогалини контенту по розділах.
- **Мовний розділ → країна.** Як додатковий сигнал додати опублікований Wikimedia набір переглядів за
  країнами з диференційною приватністю (перевірити покриття й пороги відсікання). Також додати явне
  правило в `check`: попереджати, коли у відповіді з'являються назви країн замість розділів. Haiku робив
  так в evals попри правило в `SKILL.md`.
- **Перевірки якості тексту.** `check` уже ловить вигадані числа й текст іншим письмом. Додати виявлення
  спотворених слів (словник або перевірка n-грамами) і відповідність вердикту в тексті вердикту в даних
  («зростає», коли в даних `declining`).

## v0.3 — статистика для довших і складніших рядів

- STL-декомпозиція замість помісячного десезоналізування, щоб краще обробляти теми з сильною і
  змінною сезонністю (освіта: вересень / травень).
- Виявлення точок зламу (PELT / binary segmentation), щоб відділяти стійку зміну рівня від тренду й
  пояснювати «що сталося у квітні».
- Короткий прогноз з інтервалом (ETS / сезонна наївна модель) для питань «що буде до запуску курсу».
- Коли порівнюється багато пар «тема × розділ», застосовувати корекцію множинних порівнянь (FDR
  Бенджаміні–Хохберга). Інакше серед 60 пар кілька «значущих» трендів з'являться випадково.
- Калібрування порогів довіри на історичних даних: взяти ряди з відомою подальшою динамікою і
  перевірити, як часто `high` справджується. Пороги в `references/methodology.md` зараз експертні.

## v1.0 — продукт, а не разовий аналіз

- **Моніторинг.** Збережені «радари» (теми × розділи), запуск за розкладом, `diff` з попереднім станом
  і сповіщення, коли вердикт або довіра змінюються.
- **MCP-сервер** поверх тих самих команд для агентів, які не підтримують Agent Skills, і для
  використання з інших застосунків.
- **Паралелізм агента.** Для великих досліджень давати субагенту по одному розділу чи групі тем, а
  основному агенту лише зведення. `results.json` вже має стабільну схему для злиття.
- **CI для evals на Haiku:** 3+ прогони на кейс, розширений набір кейсів (рідкісні мови, теми з
  сильними сплесками, запити без чітких розділів), LLM-суддя за рубрикою для якісних ознак, які не
  ловлять регулярні вирази (нормалізація, коректні причини довіри, мова ≠ країна).

## Масштабування на більші обсяги даних

Зараз кожна пара «стаття × розділ» — окремий запит до Pageviews API (≤170 запитів/хв з урахуванням
лімітів Wikimedia). Для сотень пар це хвилини, для тисяч — години. План:

1. **Кеш і інкрементальність.** SQLite-кеш уже зберігає покриття по датах і довантажує лише відсутні
   інтервали. Наступний крок — спільний кеш для команди (один файл на мережевому диску або
   Postgres) і фонове оновлення останнього місяця.
2. **Дампи замість API** для тисяч статей: щомісячні файли `pageview_complete` (усі статті всіх
   розділів) завантажуються й агрегуються локально (DuckDB/Polars), а API лишається для точкових
   уточнень і `verify`.
3. **Попередньо агреговані зрізи.** Частки на 1 млн за темами (категоріями) і розділами можна
   рахувати за розкладом. Тоді запит агента — читання таблиці, а не збір даних.
4. **Бюджет запиту.** Уже зараз скіл радить тримати запуск ≤60 пар. Далі — оцінювати кількість
   запитів до виконання і пропонувати агенту звузити запит або перейти на дампи.
